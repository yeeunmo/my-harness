# 작업 흐름 (story-work)

- 대상 작업: 허들링 앱 화면 디자인을 손으로 만들었던 실제 순서
- 이 문서는 "내가 실제로 어떻게 했는지"다. "무엇을 위한 일인지"는 `story-service.md`에 있고, 둘을 섞지 않는다.

## 손으로 했던 순서

| # | 문장 | 표시 |
|---|---|---|
| 1 | 나는 uibowl에서 경쟁사 레퍼런스를 수집한다. | |
| 2 | 나는 레퍼런스를 토대로 분석하고 우리 서비스에 반영할 부분을 가져온다. | **멈칫** — 뭘 가져올지 기준이 없어서 |
| 3 | 나는 분석 내용을 토대로 우리 서비스 화면 설계 문서를 구체화한다. | |
| 4 | 나는 Figma에 레퍼런스와 화면 설계서를 반영한 UI 키스크린 2~3개를 390×844 사이즈로 그린다. | |
| 5 | 나는 내부 관계자들과 협의 후 컨셉 시안을 확정한다. | **넘김** — 내부 관계자 (사람) |
| 6 | 나는 컨펌된 시안을 기반으로 디자인 토큰과 컴포넌트를 제작하고 화면 디자인에 들어간다. | |
| 7 | 나는 완성된 시안에서 토큰이나 컴포넌트가 우리 가이드에 위반된 부분이 없는지 검토한다. | **멈칫** — 가이드 위반을 눈으로 찾아야 해서 |

### 참고 (넘김은 아니지만 하네스 설계 때 볼 것)
- 1: uibowl — 도구
- 4, 6: Figma — 도구 (하네스에서 Figma를 쓸지 HTML로 바꿀지는 보류 중)
- 7: 실제로는 내가 직접 검토했다. 하네스에서는 만든 에이전트와 분리해 **읽기전용 판정자**가 맡는다.

> `story-service.md`의 "어기면 안 되는 것"은 여기 재료가 아니라 판정 기준이다. R5에서 게이트 조건으로 연결한다.
